## 三、决策项结论（3 项）

### D1｜库存查询页默认列 → **10 列全显示 + 窄屏横向滚动**

- **决议**：接受横向滚动（表格 `min-width` 撑开），不做窄屏隐藏列
- **落地状态**：B 已实现（`94fd303`），实际 10 列：`sku_code / sku_name / spec / location_code / batch_no / expiry_date / qty_on_hand / qty_allocated / qty_available / base_uom`
- **依据**：`inventory` 唯一键为 `unique (sku_id, location_id, batch_no, expiry_date)`，同一 SKU 同一库位可有多行（多批次）。不显示批次会出现多行看起来重复、无法解释的情况。仓管宁可横向滚动，也不愿点开详情才发现规格不对。

### D2｜库存分配粒度 → **按明细行（部分成功）**

- **决议**：长期按明细行分配，支持部分成功响应（`allocated: N, failed: M`）
- **Sprint 1 现状**：仍是**整单 409**，不改
- **Sprint 2 动作**：改造分配接口为按行处理 + 契约增加部分成功结构（升 v1.1）
- **依据**：仓库实际作业中「多数行有货、个别行缺货」是常态，按整单会让 1 行缺货卡住 2 行有货

### D3｜部分收货后的单据状态 → **留在 RECEIVED**

- **决议**：部分收货后单据仍为 `RECEIVED`，允许继续收货；「已收 ≥ 订货」后才转 `PUTAWAY`
- **依据**：若部分收货即转 `PUTAWAY`，剩余未到数量无处安放，只能另开新单，会造成同一采购批次拆成多张单，对账困难

### C6 详细说明（唯一带风险的决议）

| 项 | 现状 |
|---|---|
| 契约要求 | `required: true` |
| 后端接收 | ✅ 5 个写接口都接收 |
| 重放校验 | ❌ 未实现 |
| 重复提交实际结果 | 409 `INVALID_STATUS_TRANSITION` |

- **数据安全**：状态机 + `txn_no` 唯一双重保护，库存不会重复扣减
- **真实风险**：弱网重试时 UI 谎报失败
- **过渡方案**：前端「写操作失败后先 `GET` 单据，目标状态已达成则视为成功」
- **Sprint 2 正解**：加幂等记录表（key → 响应快照），同 key 重复返回首次响应，届时升 v1.1
