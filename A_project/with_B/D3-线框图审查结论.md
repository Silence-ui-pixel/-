## 三、D3 上要敲定的 3 个点（B 已主动提出，我附上我的倾向和理由）

### 点 1：「可用库存」是否唯一主列口径

- B 问：库存查询页，是否「可用库存」是唯一主列，现有/已分配仅作参考列
- **我的倾向：是，但保留现有/已分配两列可切换显示**
- 理由：作业员日常关心的是「能拣多少」=可用；但盘点/对账时要看「账面总量」=现有。两者都要，但**主次分明**：默认主列「可用」，现有/已分配作为次要列（可勾选显示或鼠标悬停查看）。
- **待定细节**：列表默认显示哪几列？我建议默认「SKU编码+名称、库位、可用库存、单位」，点开详情/流水再看批次、效期、现有、已分配。

### 点 2：O4 分配失败（409）错误结构

- B 要求 `detail` 带「需求量 / 可用量 / 差异」三个数，与 TC-02 对齐
- **我的倾向：完全同意，且这就是我在 apply-txn-cases.md TC-02 里定的口径**（异常 detail 含需求 40、可用 30、差异 10）
- **要补一个**：`detail` 里除了这三个数，还要带上**哪个 SKU/批次缺货**（`sku_code` + `batch_no`），因为一张出库单可能多行，前端要能定位到「具体哪一行缺货」，否则只显示数字用户不知道缺的是哪个货。
- **结论**：409 结构定为 `{ code: "INVENTORY_INSUFFICIENT", message, detail: { sku_code, batch_no, required, available, shortfall } }`

### 点 3：B5 收货是否落 stock_txn（收货即落账 vs 上架才落账）

- B 倾向「收货即落账」（方案 A）
- **我的倾向：同意方案 A，且这正是我在 api-list 第六节定的**（收货进暂存位即落 RECEIPT 流水，暂存位也是库位，账必须实时）
- **但这里有个必须跟 B 讲清楚的技术含义**：如果「收货即落账」，那么收货后商品在 `location_type=RECEIVING` 的暂存位上，此时「可用库存」已经 >0 了。B 的库存查询页如果设了「只看有货（可用>0）」的筛选，**收货完但还没上架的商品也会出现在查询结果里**。
  - 这是**正确的**（货确实已经在仓库里了），但作业员可能困惑「怎么货还在暂存区就显示有库存了」。
  - **解决**：库存查询页加一个「库位类型」筛选（`location_type`），默认可以排除 RECEIVING 暂存位，或让用户自己选。这个 B 的草图里**没提**，是 D3 上我要补充的。
