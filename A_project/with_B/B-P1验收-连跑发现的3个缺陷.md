# B · P1 验收（20 单连跑）发现的 3 个缺陷

> 作者：B · 日期：2026-10-27
> 触发方式：按 `02-kickoff-plan.html` 的 P1 验收标准跑「20 单连跑 + 并发不超卖 + 异常可回滚」
> 复现脚本：`web/scripts/acceptance-20-orders.mjs`（无依赖，`node` 直接跑）
> 结论：**「并发扣减不超卖」这条红线不达标**，另有 2 个连带缺陷。单线程连跑本身没问题（20 轮全通）。

---

## 一句话

`allocate` 在并发下会**丢更新**：两张单都返回 200「分配成功」，但库存只锁了一份;随后取消其一，`allocated` 被减成负数，触发 `ck_inv_allocated` 约束 → **500**，单据卡在 ALLOCATED，账实立刻不一致。

---

## 缺陷 1（严重 · P1 红线）｜并发分配丢更新

### 现象

干净库（13 SKU / 14 维度），对同一 SKU 备货 20 后，建两张各要 13 的出库单，**同时**发 allocate：

```
分配响应 200/200        ← 两张单都"成功"
已分配 13 / 现有 20     ← 但库存在账上只锁了 13，不是 26
```

### 证据（stock_txn）

```sql
select id, txn_type, location_id, allocated_delta, ref_id, remark
  from stock_txn where sku_id = ? order by id;
```

```
 42 | ALLOCATE | 1 | 16.000 | ref OUT-…859082 | 分配 OUT-20261027-859082
 43 | ALLOCATE | 1 | 16.000 | ref OUT-…8A3D53 | 分配 OUT-20261027-8A3D53
```

两条 ALLOCATE 各 +16 都落了流水（合计应 +32），但 `inventory.qty_allocated` 最终只有 16（另一次测试中是 13）。
→ 典型的 **lost update**：两个事务都读到 `available=20`（都判断 13 ≤ 20 通过），写入时是**赋值**而不是**增量**，后写的覆盖先写的。

### 后果（比"超卖"更隐蔽）

- 两张单的明细都显示"已分配"，拣货时才发现货不够 → PDA 现场报错
- 库存账面上少锁了一份货 → 可能被第三张单再次分配 → 真正超发
- 取消时按单据释放，会减成负数 → 见缺陷 2

### 建议修复

1. **读要加行锁**：`select … from inventory where … for update`（FEFO 选批那条 SQL 同样要锁）
2. **写必须是增量**，不要赋值：
   ```sql
   update inventory set qty_allocated = qty_allocated + :delta, version = version + 1
    where id = :id and qty_on_hand - qty_allocated >= :delta
   ```
   带上 `qty_on_hand - qty_allocated >= :delta` 条件，影响行数为 0 就抛 `INVENTORY_INSUFFICIENT`
3. 或用已存在的 `version` 列做乐观锁：`where id=:id and version=:expected`，冲突重试或报错
4. 补一条并发单测：`asyncio.gather` 两个 allocate，断言「成功数 × 单量 ≤ 可用量」

## 缺陷 2（严重）｜取消出库单 500（约束炸）

### 现象

清理并发测试的两张单时，第二张取消返回 **500**：

```
取消响应 200/500
```

### 证据（canku-api 日志）

```
sqlalchemy.exc.IntegrityError: (asyncpg.CheckViolationError)
new row for relation "inventory" violates check constraint "ck_inv_allocated"
```

### 根因

缺陷 1 导致行上 `qty_allocated` 只有 13（而不是 26）。取消第一张单释放 13 → 行变 0；取消第二张时再减 13 → **-13 < 0**，被 `ck_inv_allocated` 拦下 → 500。

### 后果

- 单据永久卡在 `ALLOCATED`（取消失败，也无法再分配）
- 分配锁泄漏，对账立刻出现 `diff_allocated ≠ 0`
- 用户看到 500，没有任何可操作提示

### 建议修复

1. 根因随缺陷 1 一起修
2. 取消时**按实际锁定量释放**（读该单明细的 `qty_allocated`），并用 `greatest(0, qty_allocated - :delta)` 兜底，或先校验再减
3. 加 `except IntegrityError` → 转 `409 CONFLICT`，别漏成 500

## 缺陷 3（中等 · 契约缺口）｜对账接口不带 allocated 字段

### 现象

对账出现 `MISMATCH`，但接口返回里 `diff_on_hand = 0`，页面上看起来"数字一模一样却报异常"，无法定位。

### 证据（接口返回）

```json
{ "inv_on_hand": 20, "txn_on_hand": 20, "diff_on_hand": 0, "recon_status": "MISMATCH" }
```

### 证据（视图真值）

```
 inv_on_hand | txn_on_hand | inv_allocated | txn_allocated | diff_on_hand | diff_allocated | recon_status
       20.000 |      20.000 |         0.000 |        16.000 |        0.000 |        -16.000 | MISMATCH
```

→ 真正异常的是 **allocated 维度**（`diff_allocated = -16`），但 `ReconItem` 契约只暴露了 on_hand 三项。

### 建议修复

`ReconItem` 增加 3 个字段，与视图对齐：

```yaml
inv_allocated:   { type: number }
txn_allocated:   { type: number }
diff_allocated:  { type: number }
```

前端（对账页）已在等这几个字段：现在异常行只能显示"差异 0"，改完就能直接指出"分配维度差 16"。

`ORDERS=1` 干净库跑，9 项检查 7 项通过：

| 检查项 | 结果 |
|---|---|

| 异常①：建单后取消 → 库存不变 | ✅ `CANCELLED`，库存 805/125 未变 |
| 异常②：超量分配 → 409 `INVENTORY_INSUFFICIENT` | ✅ 库存不变 |
| 异常③：重复收货 → 409 `INVALID_STATUS_TRANSITION` | ✅ 不二次入账 |
| 暂存位归零（本次无新增残留） | ✅ 4 个暂存位无残留 |
| 无负库存 / 负可用量 | ✅ 21 个维度全部非负 |
| 可用 = 现有 − 已分配（口径自洽） | ✅ 21 个维度全部成立 |
| 本次单据无卡死状态 | ✅ |
| **并发不超卖** | ❌ 缺陷 1 |
| **账实一致 100%** | ❌ 由缺陷 1+2 导致 |
