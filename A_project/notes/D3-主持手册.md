## 一、开场怎么说（30 秒，定调子）

不要念议程，直接给结论：

> "你的线框图我逐条核过，9 项判断全部对，这一部分我们直接冻结，不讨论了。
> 今天只有 3 件事要你拍板，其余 5 项我讲你点头就行。
> 最后 10 分钟我们把契约打上 tag，之后就按冻结规则走。"

**为什么这样开场**：B 会担心"是不是我哪里画错了要被批"，先给他确定性。而且明确"只有 3 件要决策"，能让他把注意力放在真正重要的地方，不会在确认项上纠缠细节。

## 二、8 张表怎么讲（10 分钟，一张表 1 句话 + 1 个反问）

**绝对不要逐字段念 schema.sql**——他看过，念一遍只会让他走神。你要讲的是「这张表存在的理由」，让他理解**设计意图**。

| 表 | 一句话（讲的原文） | 不讲会怎样（用来解释必要性） |
|---|---|---|
| `sku` | 商品主数据，一个 SKU 一行 | 同一瓶水不同规格会是两个 SKU——这是刻意的，不是设计粗糙 |
| `location` | 库位。**所有库存都挂在库位上**，没有"仓库级"库存 | 不按库位记，拣货员就不知道去哪拿 |
| `inventory` | 库存余额。`(sku, 库位, 批次, 效期)` 唯一决定一行 | 不按批次拆，就做不到 FEFO，也做不到"这箱过期了但另一箱没过期" |
| `stock_txn` | 库存流水。**只追加，永不修改删除** | 能改流水就等于能改历史，出问题永远查不出来 |
| `inbound_order` | 入库单头（供应商、状态、单号） | — |
| `outbound_order` | 出库单头（客户、优先级、状态） | — |
| `order_line` | 单据明细。**入库和出库共用一张表**，靠 `order_type` 区分 | 分两张表要写两套 CRUD、两套校验、两套测试，收益为零 |
| `app_user` | 用户 + 角色（4 种） | — |

### 讲完必须做的三个"反问"（检验他真的懂）

不要问"听懂了吗"（没人会说没懂）。**问能暴露误解的问题**：

1. **"同一个 SKU 在同一个库位，能有几行 `inventory`？"**
   → 正确答案：**4 行都可能**（不同批次 × 不同效期）。他要是答"1 行"，就说明没理解批次维度——那 D1 的默认列他会自然同意加批次。

2. **"如果要把一个商品从 A 库位挪到 B 库位，写几条流水？"**
   → 正确答案：**2 条**（A 减 + B 加）。答 1 条的说明还在用"改余额"思维。

3. **"`stock_txn` 能 UPDATE 吗？"**
   → 正确答案：**不能，数据库触发器会拦**。这题是红线，必须答对。

## 三、3 条账务不变量（10 分钟，这是全会最重要的部分）

这三条讲透，B 后面写前端就不会出方向性错误。

### 不变量 1：可用量是"算出来的"，不是"存下来的"

```
qty_available = qty_on_hand - qty_allocated     ← PG 生成列，数据库自动算
```

**要讲的话**：
> "前端永远不要提交 `qty_available`，也不要自己算。如果前端算一次、后端算一次，一定有一天两个数不一样，那时候你无法判断谁对。"

**让他复述**：`qty_available` 是只读的，能不能由前端提交？→ 不能。

### 不变量 2：所有库存变动只有一个入口

```
任何库存变化 → apply_txn() → 必写 stock_txn + 更新 inventory（同一个事务）
```

**要讲的话**：
> "代码里没有 `POST /inventory` 这种接口，也不会有。想改库存只有一条路：走单据作业（收货/上架/分配/拣货/发运），由后端调 apply_txn。
> 这不是我懒，是因为一旦开了第二个写入口，账实一致就永远保证不了。"

**这条的实战意义**：他前端如果觉得"直接改库存数字更方便"，这个念头必须当场掐掉。

### 不变量 3：账实一致可被实时验证

```
Σ(inventory.qty_on_hand 按维度) == Σ(stock_txn.on_hand_delta 按维度)
```

**要讲的话**：
> "我建了一个视图 `v_inventory_recon`，跑一次就能告诉你账和流水对不对得上。
> 现在的结果是 0 条异常。以后任何一次联调发现对不上，跑这个视图就能立刻定位是哪次操作写坏了。"

**现场演示**（如果时间够，30 秒）：
```bash
bash scripts/dev.sh db-check
```
让他看到 `账实一致（非 OK 记录 0 条）`。这比讲十遍"我们会保证一致"都有说服力。

## 四、3 个决策项的应对预案

### D1（库存页默认列）—— 最可能僵持的一项

**你的核心论据**（记住这个，别绕）：
> 唯一约束是 `(sku_id, location_id, batch_no, expiry_date)`，一个 SKU 在一个库位可以有 4 行。
> 默认列不显示批次 → 4 行长得一模一样 → 用户以为是 bug。

**如果 B 说"列表太宽了"**：
→ 让步方案：批次和效期合并成一列（`B20261004 / 2027-01-01`），只占一列宽度。

**如果 B 说"用户先看汇总，点进去再看批次"**：
→ 这是个合理诉求，但属于**新功能**（汇总视图），不是默认列的问题。
→ 记录为「Sprint 2：库存汇总视图（按 SKU+库位聚合批次）」，本次仍按明细行显示。**不要在这次会上答应做聚合**，否则范围会失控。

**如果 B 坚持原 4 列**：
→ 接受，但明确代价："那我需要在列表做『同 SKU 多批次合并 + 展开』的交互，多 1 天工作量，排到 Sprint 2，Sprint 1 先用 6 列跑通。"——把选择权和代价一起给他。

### D2（分配粒度）—— 注意别过度承诺

Sprint 1 已经实现的是**整单 409**。如果 B 选"按明细行"，**不要当场说"我马上改"**，说：

> "这个方向我认同，但改它要动契约的响应结构（部分成功），属于 Sprint 2。Sprint 1 先用整单 409 把链路跑通，你在前端把『整单失败』的提示做好，Sprint 2 我再给你部分成功的结构。"

### D3（部分收货状态）—— 大概率无争议

如果他选"部分收货即转 PUTAWAY"，追问一句："那剩余 40 件怎么办？"——通常他自己就会发现留在 RECEIVED 更合理。

## 五、控场预案

| 情况 | 怎么处理 |
|---|---|
| B 说"这块我不太懂" | 立刻降到具体场景："假设现在来了一车货 100 箱，你扫第一箱会发生什么？"用场景代替概念 |
| B 提出一个你没准备的问题 | **不要现场想答案**。说"这个我记下来，24h 内书面回你"，写进待办。现场硬答容易埋错 |
| 两人对某个字段理解不同 | 停下来，各自说出"你认为它存的是什么"，通常 1 分钟内能发现是一个词两种意思（如"库存"=现有 vs 可用） |
| 单项超时 7 分钟 | 记「待定 + 责任人 + 期限」，往下走。**议程跑完比每项都完美更重要** |
| B 开始聊实现细节（用什么库、怎么写） | 拉回来："这是实现问题，冻结完再聊，现在只定『是什么』" |
| 出现第三个方案 | 记录，但不现场评估。说"先按我的方案走，你的方案记进 Sprint 2 候选" |

## 六、冻结动作清单（会议最后 10 分钟，当场做完）

```bash
cd /d/AGENT_PROJECT/Canku_project
```
