## 一、判定方法（先说清"能算"的标准）

一条指标算"能算"，必须同时满足三条，缺一条就算"算不出来"：

| # | 标准 | 不满足会怎样 |
|---|---|---|
| 1 | **数据已经落库** | 只在接口响应里出现过、没写进表的数据，事后查不到 |
| 2 | **不依赖人工补录** | 要靠人额外填的，三个月后必然没人填 |
| 3 | **口径能用一句话说清** | 说不清的指标，两个人算出来永远是两个数 |

> 第 3 条最容易忽略。比如"库存准确率"，财务理解的、仓管理的、我理解的往往是三件事。

### 本文的 SQL 全部实跑验证过

下面每条"能算"的指标，SQL 都在 `canku` 库真实执行过（不是纸上推演）。实跑抓出 **2 个错误**：

| 错误 | 原因 | 已修正 |
|---|---|---|
| `function round(double precision, integer) does not exist` | `percentile_cont` 返回 double，PG 不能直接 round(x,2) | M1 加 `::numeric` |
| `column i.created_at does not exist` | `inventory` 表**只有 `updated_at`**，没有 `created_at` | M4 改用 `updated_at` |

这两条如果只在文档里写、不跑一遍，交到 B 手上做报表时会各卡半小时。

## 三、能算的（附可直接跑的 SQL）

### M1｜订单履约周期 ✅

**定义**：出库单从创建到发运的平均耗时（同时看 P50 / P90，平均值会被极端值带偏）

```sql
select
  count(*)                                                   as shipped_orders,
  round((avg(extract(epoch from shipped_at - created_at))/3600)::numeric, 2)   as avg_hours,
  round((percentile_cont(0.5) within group (
    order by extract(epoch from shipped_at - created_at))/3600)::numeric, 2)  as p50_hours,
  round((percentile_cont(0.9) within group (
    order by extract(epoch from shipped_at - created_at))/3600)::numeric, 2)  as p90_hours
from outbound_order
where status = 'SHIPPED'
  and shipped_at >= now() - interval '30 days';
```

> ⚠️ `percentile_cont` 返回 `double precision`，PG 没有 `round(double, int)`，**必须显式转 `::numeric`**，否则报 `function round(double precision, integer) does not exist`。（这条是我实跑时踩出来的，原文写法跑不通）

- **依赖字段**：`created_at`、`shipped_at`、`status` — 全部已有
- **口径一句话**：从建单到发运的平均小时数
- **为什么要 P90**：平均值 8 小时可能藏着"90% 在 2 小时内、10% 拖了 3 天"，P90 才暴露长尾

### M2｜准时发运率 ✅

**定义**：实际发运时间 ≤ 要求发运时间的单据占比

```sql
select
  count(*)                                                        as total,
  count(*) filter (where shipped_at <= requested_ship_at)         as on_time,
  round(100.0 * count(*) filter (where shipped_at <= requested_ship_at)
        / nullif(count(*), 0), 1)                                 as on_time_pct
from outbound_order
where status = 'SHIPPED'
  and requested_ship_at is not null
  and shipped_at >= now() - interval '30 days';
```

- **依赖字段**：`shipped_at`、`requested_ship_at` — 已有
- **注意**：`requested_ship_at` 是 `date` 类型，比较时按当天 23:59 算才合理（需在应用层处理，或 SQL 里 `shipped_at::date <= requested_ship_at`）

### M3｜数量差异率 ✅（推荐，但要改名字）

**定义**：拣货数量与要求数量不一致的明细行占比

```sql
select
  count(*)                                                as picked_lines,
  count(*) filter (where qty_actual <> qty_required)      as diff_lines,
  round(100.0 * count(*) filter (where qty_actual <> qty_required)
        / nullif(count(*), 0), 2)                         as diff_pct
from order_line l
join outbound_order o on o.id = l.outbound_id
where l.order_type = 'OUT'
  and o.status in ('PICKED', 'SHIPPED')
  and l.qty_actual is not null
  and o.created_at >= now() - interval '30 days';
```

- **依赖字段**：`qty_required`、`qty_actual` — 已有
- ⚠️ **必须改名**：不能叫"拣货准确率"。系统只知道扫了哪个 SKU/批次，**拣错货（拿了 A 记成 B）系统根本发现不了**。叫"数量差异率"才诚实
- **这是很重要的一次口径收缩**：宁可指标难看但真实，不要指标好看但骗人

### M4｜库存呆滞率 ✅（备选）

**定义**：超过 30 天没有任何流水的库存记录占比

```sql
with last_move as (
  select sku_id, location_id, batch_no, expiry_date, max(created_at) as last_txn_at
  from stock_txn
  group by sku_id, location_id, batch_no, expiry_date
)
select
  count(*)                                                            as total_rows,
  count(*) filter (where coalesce(lm.last_txn_at, i.updated_at) < now() - interval '30 days')
                                                                      as idle_rows,
  round((100.0 * count(*) filter (where coalesce(lm.last_txn_at, i.updated_at) < now() - interval '30 days')
        / nullif(count(*), 0))::numeric, 1)                           as idle_pct
from inventory i
left join last_move lm
  on  lm.sku_id = i.sku_id and lm.location_id = i.location_id
  and lm.batch_no = i.batch_no and lm.expiry_date = i.expiry_date
where i.qty_on_hand > 0;
```

> ⚠️ `inventory` 表**没有 `created_at`**，只有 `updated_at`（字段清单：id / sku_id / location_id / batch_no / expiry_date / qty_on_hand / qty_allocated / qty_available / version / updated_at）。原文用 `i.created_at` 会直接报错，必须用 `updated_at` 兜底。

- **依赖字段**：`stock_txn.created_at`、`inventory` — 已有
- **用途**：找压在库里的死货，是仓储最实在的省钱指标

### M5｜账内一致率 ✅（但别当业务指标）

```sql
select
  recon_status,
  count(*) as rows,
  round(100.0 * count(*) / sum(count(*)) over (), 2) as pct
from v_inventory_recon
group by recon_status;
```

- **必须说清楚**：这个算的是「**余额 vs 流水累计**」，是系统**自己跟自己对**，属于**系统健康度**，不是「账 vs 实物」
- 拿它当"库存准确率"汇报给老板，是**误导**。一旦被追问"那实际货对不对"，会答不上来

## 四、算不出来的（必须做决定）

### M8｜库存准确率 ❌ → 建议砍掉，或 Sprint 2 补盘点表

**为什么算不出来**：8 张表里**没有盘点单/盘点明细表**。

真正的库存准确率需要：
```
盘点记录（某天某库位实际有多少） vs 系统账面（同一天同一库位）
```
现在系统只有账面，没有"实际数"的采集入口。

**三个选项**：

| 选项 | 做法 | 代价 | 建议 |
|---|---|---|---|
| A. 砍掉 | 不报这个指标 | 0 | **Sprint 1 选这个** |
| B. 用账内一致率冒充 | 报 M5 | 0，但会误导 | ❌ 不要 |
| C. 补盘点表 | 加 `stocktake` + `stocktake_line` 两张表 + 3 个接口 | 约 2 人天 | Sprint 2 做 |

> **我的判断**：Sprint 1 砍掉。理由：没有盘点数据支撑的准确率是假的，报了反而让人以为"系统能管账实"，实际上管不了。

### M9｜缺货率 ❌ → 建议 Sprint 1 砍掉（补字段比想象中贵）

**为什么算不出来**：分配失败时抛 409 `INVENTORY_INSUFFICIENT`，这个信息**只返回给前端，没有写进任何表**。事后查"这个月缺了多少次货"，系统一无所知。

**我原本以为补个字段就够，实测后发现没那么简单**：

`order_line.status` 的 check 约束是：

```sql
constraint ck_line_status check (status in
  ('OPEN','ALLOCATED','PARTIAL','DONE','CANCELLED'))
```

三个障碍：

1. **没有 `SHORT` 这个值** —— 加它要改 check 约束 → 必须一次 alembic 迁移
2. **`PARTIAL` 已被占用** —— 现有代码 `outbound_orders.py:535` 用它表示「拣货量 ≠ 锁定量」，语义是"部分拣货"，拿来标"缺货"会让两个概念混在一个字段里
3. **整单失败不落明细** —— Sprint 1 的分配是整单 409，失败时**一行明细都不会被写**，连 `remark` 都没机会落

**三个选项**：

| 选项 | 做法 | 代价 | 建议 |
|---|---|---|---|
| A. 砍掉 | Sprint 1 不报缺货率 | 0 | ✅ **推荐** |
| B. 加 `SHORT` 枚举 | check 约束加值 + 改分配失败分支 + 改契约 + 补测试 | 约 2 小时（含迁移） | 等现场确认痛点后再做 |
| C. 用 `remark` 存固定格式 | `remark = "SHORT:缺10"`，SQL 里 LIKE 匹配 | 30 分钟 | ❌ 字符串匹配太脆弱，改个文案就全错 |

> **我的判断**：Sprint 1 砍掉。
> 理由：现在改约束意味着**动已冻结的结构**，为一个尚未被现场证实的指标不值得。等 S1-01 回来，如果"缺货是核心痛点"，再按选项 B 正经做（那时正好进 Sprint 2）。

**如果一定要现在有数据**：最诚实的替代是「**分配失败次数**」——但这个数也不落库，同样没有。所以只能靠应用日志抓，不在指标体系里。

## 五、推荐的 3 个指标（对应 3 个痛点）

> ⚠️ 下面 3 个痛点是**技术视角的候选**，不是调研结论。真实痛点必须 S1-01 回来后再定，可能与这里完全不同。

| # | 痛点（待现场确认） | 指标 | 口径 | 数据来源 |
|---|---|---|---|---|
| P1 | 单子积压，不知道卡在哪个环节 | **履约周期 P50/P90** | 建单到发运的小时数 | `outbound_order` |
| P2 | 答应客户的时间老做不到，只能事后道歉 | **准时发运率** | 实际 ≤ 要求 的占比 | `outbound_order` |
| P3 | 发出去的数量老不对，客户投诉才发现 | **数量差异率** | 实拣 ≠ 应拣 的行占比 | `order_line` |

**为什么选这 3 个**：

1. **全部能算**，不依赖任何补字段或人工补录
2. **每天自动产生数据**，不需要额外动作（这是关键——需要人额外填的指标活不过三个月）
3. **能直接指向改进动作**：周期长→查哪个环节慢；准时率低→查排产；差异率高→查复核环节
4. 分属**效率 / 服务 / 质量**三个维度，不重复

## 附：为什么"能算"比"想算"重要

写这份矩阵前，我列了 9 个看起来很合理的仓库指标。判定完只剩 5 个能算。

**如果跳过这一步直接跟老板汇报"我们能算库存准确率和缺货率"，后果是**：
- 第一周：报表页做不出来，才发现没有盘点数据
- 第二周：临时用账内一致率顶替，汇报时被问穿
- 第三周：承诺"下周补"，实际要 2 人天，Sprint 1 延期

**现在花 1 小时判定，省下的是 3 周返工。** 这就是这个任务存在的意义。
