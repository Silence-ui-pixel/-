## 🔧 本轮修复详情（B 联调反馈驱动）

**B 的报告**：`A_project/with_B/B-联调反馈-错误响应格式.md`

### 问题本质

只有 `DomainError`（业务错误）走了契约格式，FastAPI 内置的 3 类异常仍是默认 `{detail}`：

| 异常来源 | 修复前 | 修复后 |
|---|---|---|
| `DomainError` | ✅ 契约格式 | 不变 |
| `HTTPException` | ❌ `{detail}` | ✅ `{code, message, detail}` |
| `RequestValidationError` | ❌ `{detail: [...]}` | ✅ `VALIDATION_ERROR` + `detail.errors` |

### 关键决策：`detail` 用 `{}` 不是 `null`

B 建议写 `detail: None`，**我没照做** —— `contracts/openapi.yaml` 里 `detail` 声明为 `type: object` 且无 `nullable`，返回 `null` 会违反契约，前端若做 schema 校验会直接炸。统一给 `{}`，前端可以永远 `err.detail ?? {}`。

### 改动文件

| 文件 | 改动 |
|---|---|
| `api/app/main.py` | 加 `StarletteHTTPException` + `RequestValidationError` 两个处理器；**保留原异常 headers**（401 的 `WWW-Authenticate` 不能丢） |
| `api/app/core/errors.py` | 加 `HTTP_STATUS_TO_CODE` 映射表（11 个状态码）+ `clean_validation_errors()`（洗掉 Pydantic 里不可序列化的 `ctx.error` / `bytes input`） |
| `api/app/schemas/__init__.py` | `InventoryItem` 加 `spec: str \| None` |
| `api/app/api/v1/inventory.py` | 查询带出 `sku.spec` |
| `contracts/openapi.yaml` | `InventoryItem.spec`（`nullable: true`） |

### 两个隐蔽坑（值得记住）

1. **Pydantic 的 `ctx` 可能塞着 `ValueError` 实例、`input` 可能是 `bytes`** → 直接 `JSONResponse` 会抛 "not JSON serializable" 变成 500，把「参数错了」误导成「服务器崩了」。`clean_validation_errors()` 统一转成原始类型。
2. **`detail` 类型必须与契约一致** → 这是「契约唯一真源」原则的实战检验：B 的建议在语义上合理，但在契约上非法，不能照抄。

### Docker Desktop 重启后，旧容器挂载会失效 ⚠️

**症状**：`docker compose up` 后容器起来了，但 API 报 `ModuleNotFoundError: No module named 'app'`，
容器内 `/app` 是空目录（`ls /app` 无输出）。

**原因**：Docker Desktop 停止期间，旧容器（几小时/几天前创建的）的 bind mount 失效，
即使重新 `up` 也不会重新绑定。

**解决**：重建容器即可（数据在 named volume `pgdata` 里，不会丢）：

```bash
docker compose down && docker compose up -d
```

**验证**：`docker compose exec -T api ls /app` 应能看到 `app/` `alembic/` 等目录。

### 命令行里不能用 Unix shell 语法去跑 Win32 终端

- `docker compose exec ... < file` ← 在 Win32 终端里 `<` 不是重定向（报 `RedirectionNotSupported`）
- `cd /d/AGENT_PROJECT/...` ← 会被拼成相对路径，要用 `cd D:\AGENT_PROJECT\...`

**规避**：用 Git Bash，或用 `bash scripts/dev.sh xxx` 走脚本（脚本内部是 bash）。

### 第 3 批的作业语义速查（面试/交接时讲得清）

| 动作 | 库存怎么变 | 为什么 |
|---|---|---|
| 收货 RECEIPT | RECEIVING 位 +N | 货到了但没上架，账上必须有 |
| 上架 TRANSFER_OUT + PUTAWAY | RECEIVING −N，STORAGE +N | 库存按库位记，一次移库必两条流水 |

| 发运 SHIP | STAGING −N | 货真正离仓 |
| 取消 DEALLOCATE | allocated −N | 不放回就是永久性库存泄漏 |

## ⚠️ 已知限制（Sprint 1 明确不做，不是 bug）

1. **不支持跨批次分配**：一条出库明细只能绑一个批次/库位。不足直接 409 并提示拆单。跨批次需 allocation 明细表，属 Sprint 2。
2. **不支持多次部分收货**：一次收货完成整单（否则 txn_no 失去天然幂等）。
3. **批次商品未强制效期**：只强制批次号，效期缺省用哨兵 9999-12-30。
4. **商品主数据无审计表**：写操作只落结构化日志，正式审计表属 Sprint 2（`skus.py` 注释已写明）。
5. **商品修改不开放 sku_code / barcode**：契约未给，编码变更会影响历史单据指向。
6. **`Idempotency-Key` 已声明但未做重放校验** ⚠️ 契约要求必带（openapi 第 63 行 `required: true`），5 个写接口都接收了该头，但**没有任何代码使用它**。实测重复提交返回 409 而非幂等成功。
   - **数据安全没问题**：状态机 + `txn_no` 唯一双重保护，库存绝不会重复扣减
   - **问题是 UI 骗人**：弱网重试时用户看到「失败」，实际上一次已成功
   - **当前对策**：前端「失败后先 GET 单据状态再决定报错」（已写进 `with_B/B-接口调用红线与开发约定.md` 第 2.4 节）
   - **正解**：Sprint 2 加幂等记录表（key → 响应快照），同 key 重复直接返回首次响应。届时要改契约语义，属 v1.1
   - **已正式登记**：`contracts/CONTRACT-FREEZE.md` 第五节「冻结时已知欠账」第 1 条，不算违约
7. **FEFO 会把过期批次发出去** 🔴 **P0 · 现场确认后定性升级为「实现与作业规范正面冲突」**
   - 分配时只按 `expiry_date` 升序选批次，**不检查是否已过期**
   - 实测：出库 10 箱 SKU0006 牛奶，FEFO 选中批次 `B20260201`（效期 2026-08-01，**过期 85 天**）
   - 导入库存里 5 个批次已过期共 245 箱，其中 **4 个批次已在「已分配」状态**（等着发出去）
   - **定性升级**：业务方书面确认「拣货看效期，FEFO（近效期先出）」
     → 系统的分配逻辑违背现场作业规范，不再是「算法偏好取舍」问题
   - **修复**：分配查询加 `expiry_date >= current_date`，约 1 小时（1 条件 + 1 测试 + 契约补一句）
   - **✅ 已修（2026-10-25）**：`allocation_service.py` 加 `expiry_date >= func.current_date()`，新增 2 测试
   - 延伸：过期品当前无报损能力（`ADJUST` 流水类型有，但没有报损单据），245 箱会一直挂账 → Sprint 2「报损单」

8. **不支持分次收货** 🔴 **P0 · 现场确认「一车货会分两次到」，假设 1 被推翻**
   - 当前实现：第一次收货即无条件置 `RECEIVED`，`txn_no = RECEIPT-{单}-{行}` 无序号，`qty_actual` 是覆盖不是累加
   - 实测：计划 100 件，收 40 件 → 单据变 `RECEIVED`；第二批 60 件到货 → **409 拒绝**
   - 三条补救路全堵：再收被状态机拒 / 改明细只允许 `DRAFT` / 新建单与供应商送单对不上
   - 讽刺点：状态机里 `RECEIVING` 状态**早就定义好且 `_RECEIVABLE` 也包含它**，只是实现没接上
   - **✅ 已修（2026-10-25）**：`txn_no` 加序号、`qty_actual` 累加、状态按「是否收满」判断。真实 HTTP 验证：收 40→RECEIVING/PARTIAL，再收 60→RECEIVED/DONE
   - ⚠️ **需通知 B**：收货响应 status 语义变了（收满才 RECEIVED），前端入库作业台收货页要跟着改

9. **改单/取消无角色校验** 🟡 **P1 · 与现场约定「只有主管能改」不符**
   - `router` 有全局 `get_current_user`（未登录进不来，**不是漏洞**），但没有角色判断
   - 后果：`VIEWER`（财务/老板只读角色）能取消入库单，`OPERATOR` 也能取消主管才能取消的单
   - **✅ 已修（2026-10-25）**：`security.py` 新增 `require_role(*roles)` 依赖工厂；入出库「取消」+ 入库「改明细」三处加 `require_role("MANAGER", "ADMIN")`。真实 HTTP 验证 OPERATOR 取消 → 403 FORBIDDEN
