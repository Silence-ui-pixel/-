1

三条铁律

后面所有代码都必须服从，违反一条账就不准
库存只有一个写入口
全系统只有 stock_service 能改 inventory。任何模块想动库存，必须调它。禁止绕过入口直接 UPDATE——这是账实不一致的第一大来源。
改余额必写流水
改 inventory 和写 stock_txn 必须在同一个事务里，且流水带上 before_on_hand / after_on_hand 快照，可逐笔复算。
流水只追加，永不修改
stock_txn 上挂了触发器，数据库层面直接拒绝 UPDATE / DELETE。审计链断了就再也拼不回来。

3
location库位主数据
整个模型里最容易被过度设计的一张表。很多人上来就做 warehouse → zone → rack → level → bin 五张表的递归树，结果为了查一个库位要 join 四次。
字段类型说明
PKidbigserial主键
warehouse_codevarchar(32)仓库编码，默认 WH01。单仓也要留，改多仓时不用改结构
zone_codevarchar(32)库区，如 A / COLD / HAZ
rack_codevarchar(32)货架，如 01
level_nosmallint层号
bin_codevarchar(32)位号
location_codevarchar(96)全码 WH01-A-01-03-02，唯一。扫码枪扫的就是它
location_typevarchar(16)STORAGE / RECEIVING / PICKING / STAGING / QUARANTINE
pick_seqinteger拣货顺序号。按蛇形动线编排，拣货单按它排序就是最短路径
capacity_qty / capacity_volumenumeric容量上限，上架推荐时做约束
is_mixed_sku / is_mixed_batchboolean是否允许混放 SKU / 批次。上架校验用
statussmallint1 可用 / 0 停用（维修、封存）
created_at / updated_attimestamptz时间戳
为什么不做 parent_id 递归：仓储层级是固定的四层，永远不会变。扁平冗余列 + 全码字符串，让「查某库区所有库位」「按拣货顺序排序」都变成单表查询，不用递归 CTE。这是用一点存储冗余换掉一整类性能问题和复杂度。
4
inventory库存余额核心 · 唯一写入点
全系统只有一个服务能写这张表。唯一维度是 SKU + 库位 + 批次 + 效期，四个字段共同决定一行库存。
字段类型说明
PKidbigserial主键
FKsku_idbigint商品
FKlocation_idbigint库位
batch_novarchar(64)批次号，默认空串而不是 NULL（见下方说明）
expiry_datedate效期，默认哨兵值 9999-12-31
qty_on_handnumeric(14,3)现有量（物理在库），约束 ≥ 0
qty_allocatednumeric(14,3)已分配量（被出库单锁定），约束 0 ≤ 它 ≤ 现有量
GENqty_availablenumeric(14,3)可用量 = 现有量 − 已分配量，生成列，代码不可写
versionbigint乐观锁版本号，并发扣减时用
updated_attimestamptz更新时间
为什么 batch_no 用空串、expiry_date 用 9999-12-31：PostgreSQL 里 NULL = NULL 结果是 NULL 而不是 true，所以唯一约束 unique(sku_id, location_id, batch_no, expiry_date) 在含 NULL 的行上形同虚设——同一个维度会被重复插入多行，库存直接算错。用空串和哨兵日期把 NULL 挤出去，唯一约束才真正生效。这是库存系统最常见的一个隐藏 bug。
5
stock_txn库存流水核心 · 只追加
系统的账本。每一次库存变化都必须留下一条，带变动前后的快照。能逐笔复算出当前余额，这是账实一致的技术底线。
字段类型说明
PKidbigserial主键
txn_novarchar(40)流水号，唯一，便于对账和人工排查
txn_typevarchar(24)RECEIPT 收货 / PUTAWAY 上架 / PICK 拣货 / SHIP 发货 / ADJUST 调整 / TRANSFER_IN / TRANSFER_OUT / COUNT_ADJUST 盘点 / ALLOCATE 分配 / DEALLOCATE 释放
FKsku_id / location_idbigint变动的库存维度
batch_no / expiry_datevarchar / date同上，用空串与哨兵值
on_hand_deltanumeric现有量变化。入库为正、出库为负、分配为 0
allocated_deltanumeric分配量变化。分配为正、拣货出库为负
before_on_hand / after_on_handnumeric变动前后快照，约束 after = before + on_hand_delta 强制自洽
ref_type / ref_id / ref_line_idvarchar / bigint来源单据类型、单头 ID、明细行 ID，可回溯到具体哪一行
sourcevarchar(16)WEB / PDA / AGENT / SYSTEM / IMPORT
AIagent_run_idvarchar(64)AI 发起时记下会话 / 审批单 ID。能回答「这单是哪个 Agent 哪次审批产生的」
FKoperator_idbigint操作人，系统作业可为空
remarkvarchar(500)备注，人工调整必须填写原因
created_attimestamptz发生时间，不做 updated_at —— 这行永远不会被改
为什么用两个 delta 而不是「数量 + 方向」：因为「分配库存」这个动作只动 allocated 不动 on_hand。如果只有单列 qty，这种变动表达不出来，会导致按流水汇总时对不上余额。source + agent_run_id 是给 AI 治理留的钩子——没有这两个字段，出了事根本查不到是哪个 Agent 干的。

order_line单据明细单据 · 多态
入库明细和出库明细的字段重合度约 80%，拆成两张表意味着两套几乎一样的代码。这里合并成一张，用判别列区分归属。
字段类型说明
PKidbigserial主键
order_typechar(2)IN 入库 / OUT 出库，判别列
FKinbound_idbigint入库单（order_type='IN' 时非空）
FKoutbound_idbigint出库单（order_type='OUT' 时非空）
line_nointeger行号，单内唯一
FKsku_idbigint商品

qty_rejectednumeric(14,3)不良 / 短拣数量

FKfrom_location_idbigint出库：分配的拣货库位
FKto_location_idbigint入库：上架目标库位
statusvarchar(16)OPEN / ALLOCATED / PARTIAL / DONE / CANCELLED

多态归属怎么保住外键完整性：两个可空外键 + CHECK 约束保证「恰好一个非空」，所以外键约束依然生效，只是从「非空」变成「条件非空」。唯一性不能用普通 UNIQUE（可空列在 UNIQUE 里同样有 NULL 问题），改用两个部分唯一索引：where inbound_id is not null / where outbound_id is not null。这是 PostgreSQL 里做多态表的标准手法。
4

库存一致性怎么保证

这是整个模型唯一真正难的地方

三条铁律只是原则，落地靠下面这段事务模板。所有改变库存的代码路径（收货、上架、拣货、发货、盘点、AI 建议执行）都必须走同一个函数，函数内部就是这五步。

stock_service.apply_txn() · 唯一写入口PostgreSQL
BEGIN;

-- 1) 锁定库存维度（行级锁，串行化同一 SKU+库位+批次的并发）
SELECT id, qty_on_hand, qty_allocated, version
  FROM inventory
 WHERE sku_id = :sku AND location_id = :loc
   AND batch_no = :batch AND expiry_date = :exp
   FOR UPDATE;

-- 2) 校验可用量：qty_on_hand - qty_allocated >= :qty
--    不足则抛业务异常并回滚，绝不允许负库存

-- 3) 改余额（CHECK 约束是最后一道防线）
UPDATE inventory
   SET qty_on_hand = qty_on_hand - :qty,
       version     = version + 1
 WHERE id = :inv_id
   AND version = :ver;          -- 乐观锁，影响行数为 0 则重试

-- 4) 写流水，快照必须与第 3 步结果严格一致
INSERT INTO stock_txn
  (txn_no, txn_type, sku_id, location_id, batch_no, expiry_date,
   on_hand_delta, allocated_delta, before_on_hand, after_on_hand,
   ref_type, ref_id, ref_line_id, source, agent_run_id, operator_id)
VALUES
  ('TXN...', 'PICK', :sku, :loc, :batch, :exp,
   -:qty, -:qty, :before, :after,
   'OUTBOUND', :order_id, :line_id, 'AGENT', :run_id, :operator);

-- 5) 同步单据明细与单据头汇总
UPDATE order_line   SET qty_actual = qty_actual + :qty WHERE id = :line_id;
UPDATE outbound_order SET total_qty = total_qty - :qty WHERE id = :order_id;

COMMIT;

六个刻意的设计决定

每个都能被质疑，所以写清理由
01
库位不做递归树，用扁平编码层级固定四层，永不变。扁平化让「按库区查」和「按拣货顺序排」都是单表查询，省掉递归 CTE 和五张关联表。
02
入库/出库明细合并为一张表字段重合 80%，合并省掉一套 CRUD 代码。代价是多态归属稍复杂，用 CHECK + 部分唯一索引补回完整性。
03
batch_no 空串、expiry_date 哨兵值为了让唯一约束真正生效。这是 PostgreSQL 上做库存系统的必修课，不这么写会静默产生重复库存行。
04
qty_available 用生成列而非普通列可用量在列表页、分配、AI 查询里都是高频字段。生成列保证它永远等于现有量减分配量，不可能不一致，也不占维护成本。
05
流水用双 delta 而非「数量+方向」因为「分配」只动 allocated 不动 on_hand。单列表达不了，会导致流水汇总对不上余额。
06
单据头冗余汇总字段列表页要显示总量，聚合明细在数据量上来后会很慢。代价是每次改明细要同步更新头，但这一步本来就在同一个事务里。
