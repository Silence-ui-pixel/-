仓储智能管理 Agent 系统 · 启动方案与分工

两人团队 · 从零到可试点版本 · 14 周
假设前提：2 人全职 · 单一仓库 · 无现成系统需替换 · 无复杂自动化设备 目标：14 周内交付可真实跑单的试点版本
1

先给三条判断

这部分比后面的计划更重要
不要从零写完整 WMS
两个人写不完一个商用 WMS。真正要做的是一条能跑通的最小闭环，够支撑 AI 场景即可。单据类型先只做 5 张，不要 30 张。
不要先做 AI
先把库存账做对。账是错的，AI 只会把错误放大。AI 是放大器，不是地基。所以 AI 排在第 7 周之后。
不要按想象的流程开发
第一周必须去仓库现场站着看。仓库作业有大量"系统里没有的规矩"，坐在办公室设计出来的流程上线必被推翻。
2

冷启动：前两周不要写业务代码

这两周决定项目生死
W1 一
去现场，不要开会
两人一起去仓库待一整天。跟着一个真实订单从收货走到发运，全程录像、记时间、记纸质单据。重点记三件事：他们在哪里停下来找东西、哪里用纸质/微信代替系统、哪里在重复录入。这三个位置就是产品的价值点。
W1 三
写一页纸范围声明
半页写"做什么"，半页写"不做什么"。不做什么那一页是护身符，后面所有人加需求时拿它挡。明确列出：本期不做多货主、不做波次优化、不做设备对接、不做移动 App（用 H5）。
W1 五
定 3 个核心痛点 + 3 个指标
痛点必须可量化。例如"找货平均 8 分钟"→ 目标 3 分钟；"账实差异每月 3%"→ 目标 0.5%;"补货靠拍脑袋"→ 缺货率从 6% 降到 2%。没有指标的痛点等于没有痛点。
W2 一~三
画领域模型（只画 8 张表）
商品 SKU、库位 Location、库存 Inventory、库存流水 StockTxn、入库单、出库单、单据明细、用户。就这 8 张。两人一起画，一起评审——这是全项目最重要的协作动作，模型错了后面全是返工。
W2 四~五
冻结 API 契约 + 搭骨架
用 OpenAPI 写接口定义，先生成文档和前端 client，再写实现。同时把 Docker Compose 跑起来（PG + Redis + MinIO），前端空壳能登录，CI 能跑通。验收标准：两人各自在干净机器上 30 分钟内跑起完整环境。
为什么第 2 周末要"冻结契约"

两人团队最大的成本不是写代码，是互相等待和反复对齐。契约一旦冻结，两个人就能真正并行：一个人埋头写后端实现，另一个人对着 mock 数据做前端和 Agent，中间不需要天天沟通。契约后续可以加字段，但不要改已有字段的语义。

3

技术栈定稿

原则：组件少、运维轻、AI 同语言
层选型理由
后端Python 3.12 + FastAPI与 AI 层同语言，省掉一个服务边界和一套序列化协议；两人团队最忌讳多语言
前端Vue3 + TypeScript + Element Plus表格/表单类后台生态最成熟；同一套响应式页面直接当 PDA 用，不做原生 App
数据库PostgreSQL 16 + pgvector关系数据和向量检索一个库搞定，少运维一个 Milvus；事务能力是库存账的刚需
缓存 / 队列Redis库存热点缓存 + 异步任务（盘点、预测跑批）
对象存储MinIO单据影像、验收照片、文档原件
Agent 编排自研轻量状态机优先，LangGraph 备选两人团队扛不住框架 breaking change；仓储场景的编排复杂度被高估了
模型统一网关 + 可切换（DeepSeek / 通义 / GLM）成本可控，不被单一供应商绑定，出问题能一键切
部署Docker Compose，不上 K8s单仓场景一台机器足够；K8s 的收益要 10 人团队才追得回成本

如果你的团队是 Java 背景，把后端换成 Spring Boot、前端不变即可，其余选型都成立。但不要为了 AI 再引入一个 Python 服务——两人团队维护两套语言是纯亏损。

为什么 AI 场景只做两个

两个场景刚好覆盖两种形态：只读查询（证明可用性和价值）和写操作 + 人工审批（验证治理链路能扛住）。这两条跑通，后面加第 3、4 个 Agent 只是复制工作量；这两条跑不通，做 6 个 Agent 也上不了生产。

两人分工

按模块切，不按前后端切
成员 A · OWNER
领域与账务
  • 库存账本与流水 —— 全项目最难、最核心，必须一个人从头负责到底
  • 单据状态机 —— 收货、上架、拣货、出库、盘点的状态流转与回滚
  • 库位模型与分配算法 —— 库区/货架/库位，上架推荐规则
  • 事务、并发与幂等 —— 防超卖、防重复提交、防断网重复扫码
  • MCP 工具实现 —— 工具本质就是业务写入口，必须懂业务的人写
  • 数据初始化与迁移脚本 —— 真实 SKU 导入、期初库存
成员 B · OWNER
交互与智能
  • 前端工作台 + PDA 页面 —— 列表、单据、扫码交互，一套代码两种屏幕
  • Agent 编排器与 Prompt 工程 —— 意图识别、工具选择、多轮澄清
  • 决策引擎与审批流 —— 规则校验、风险分级、审批台 UI
  • RAG 知识库 —— SOP 文档切分、检索、引用溯源
  • 报表与看板 —— 库存健康度、作业效率、AI 采纳率
  • AI 评测集 —— 30 条真实问题 + 标准答案，这是唯一能证明 AI 有效的证据
两人之间的三个交接面（只有这三个，其余不互相打扰）
A：业务能力实现 → contracts/openapi.yaml → B：前端调用
A：MCP 工具（强类型入参） → contracts/mcp-tools.json → B：Agent 调用
A：账本口径定义 ↔ 口径文档（可用/锁定/在途怎么算） ↔ B：报表展示
铁律：B 不允许直接读 A 的数据库表。所有数据必须走接口或 MCP 工具。这条规则不守，两个人一周内就会互相踩死对方的表结构，返工成本远大于写接口的成本。
如果两人技能不对等，怎么调

谁更懂仓储业务，谁就必须做 A（账不是靠技术能力做对的，是靠业务理解）。如果两人都不懂业务，那第 1 周现场调研必须加倍投入，并且要拉一个仓库主管做"业务顾问"，每周 2 小时固定答疑——这个角色比多一个程序员有用得多。如果前端能力弱，B 的前端部分可直接用 Element Plus 的 admin 模板起步，不要原创设计。

协作机制

两人团队靠节奏，不靠流程
1
周一 30 分钟对齐只定本周切片和接口变更，不做汇报
2
周三半天联调固定时间，前后端实际对接，问题当场解决
3
周五 Demo只演示能跑的东西，不接受 PPT 和截图
4
PR 强制互审两人团队唯一的代码质量关卡，不能省
5
主干开发 + 短分支单分支存活不超过 2 天，减少合并地狱
6
接口变更当日通知改契约必须同步改文档并告知对方

明确不做的事

这份清单比路线图更能保护你
前 14 周内，以下内容一律不做
多仓多货主 —— 单仓跑通再说
复杂波次策略 —— 先一单一拣
AGV / 输送线对接 —— 等有设备再谈
微服务拆分 —— 单体 + 模块化足够
自研权限系统 —— 用现成 RBAC 库
模型微调 —— Prompt + 工具调用先做扎实
原生 App —— H5 响应式就够用
6 个 Agent —— 先 2 个，跑通再加
自研报表引擎 —— 用现成 BI 或直接 SQL
K8s / 服务网格 —— Compose 到试点结束
8

四个真实会杀死项目的风险

极高
范围失控两人团队最常见的死法：每来一个新需求就加。对策：一页纸范围声明 + "换出机制"（要加新功能，必须先说砍掉哪个）。
极高
库存账实不一致库存被多处直接 UPDATE，最终没人知道真实数量。对策：库存只能有一个写入入口，所有变动必落流水，禁止任何地方直接改库存表。
高
AI 幻觉导致错误操作Agent 自信地生成一张错误单据。对策：只读优先；写操作必须过决策引擎 + 人工审批；所有动作幂等且可撤销；审计日志完整可回放。
高
两人都变成"全栈打杂"没有明确边界，谁有空谁改，三个月后代码没人说得清。对策：模块 Owner 制 + 契约隔离 + 不直读对方数据表。
